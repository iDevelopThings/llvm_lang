# go-llvm on Windows — setup (llvm_lang)

Build against [`tinygo.org/x/go-llvm`](https://github.com/tinygo-org/go-llvm)
targeting **LLVM 22** on Windows, buildable directly from GoLand (Run/Debug)
with a single build tag and no environment-variable juggling.

## What's installed / how it's wired

- **LLVM 22.1.7**, prebuilt from MSYS2 for the **mingw64** environment
  (`mingw-w64-x86_64-llvm`). No source compile — it's the same version you'd
  get from building LLVM yourself. `llvm-config`, headers, static libs, and a
  shared `libLLVM-22.dll` all live under `C:\msys64\mingw64\bin` / `\lib` /
  `\include`.
- **Toolchain match:** cgo uses `gcc`/`g++` from `C:\msys64\mingw64\bin`
  (mingw64, msvcrt runtime). The LLVM package is the mingw64 one so the C++ ABI
  matches. Do **not** mix in UCRT64/clang64 LLVM or MSVC's LLVM — the C++
  name-mangling/ABI won't match and you'll get "undefined reference" link errors.
- **go-llvm needs a `windows` cgo block, which upstream lacks.** Its per-version
  config files (`llvm_config_llvm22.go`) only define flags for darwin/linux/
  freebsd. So we keep a **local patched copy** at `third_party/go-llvm` with a
  `windows` block added, and point the module at it:

  ```
  replace tinygo.org/x/go-llvm => ./third_party/go-llvm
  ```

  The added block (in `third_party/go-llvm/llvm_config_llvm22.go`):

  ```
  // #cgo windows CPPFLAGS: -IC:/msys64/mingw64/include -D_GLIBCXX_USE_CXX11_ABI=1 -D_FILE_OFFSET_BITS=64 -D__STDC_CONSTANT_MACROS -D__STDC_FORMAT_MACROS -D__STDC_LIMIT_MACROS
  // #cgo windows CXXFLAGS: -std=c++17
  // #cgo windows LDFLAGS:  -LC:/msys64/mingw64/lib -lLLVM-22
  ```

  Because the flags now live in a `#cgo` file inside the go-llvm package, the
  only thing any build needs is the version tag **`llvm22`** — no `byollvm`, no
  `CGO_*` env vars. (`byollvm` + env is the alternative if you ever don't want
  the local patch; it's not used here.)

## Why a `replace` copy and not `vendor/`

A plain `vendor/` is regenerated by `go mod vendor`, which would overwrite the
`windows` patch. The `replace` copy in `third_party/` is a permanent source of
truth. If you later want a self-contained tree, `go mod vendor` will bake the
patch in *because* vendoring follows the replace directive.

## Reinstalling LLVM (fresh machine)

In any shell (pacman works from PowerShell too):

```powershell
& C:\msys64\usr\bin\bash.exe -lc "pacman -S --needed --noconfirm mingw-w64-x86_64-llvm"
```

## Building

### From the CLI

```powershell
.\build.ps1 -Run
# or directly:
go build -tags=llvm22 -o llvm_lang.exe .
```

Expected output: the IR for `add`, then `// go-llvm against LLVM 22.1.7 is working ✅`.

### From GoLand (native Run/Debug)

1. **Set the build tag once** (for the indexer / code analysis, so go-llvm
   resolves with no red code): *Settings → Go → Build Tags & Vendoring →
   Custom tags:* `llvm22`.
2. A ready-made **`llvm_lang`** run configuration is committed
   (`.idea/runConfigurations/llvm_lang.xml`) — it already passes `-tags=llvm22`.
   Just pick it and press **Run** or **Debug**.
3. GoLand inherits the system `PATH`, which includes `C:\msys64\mingw64\bin`,
   so `gcc`/`g++` (build) and `libLLVM-22.dll` (run) are found automatically.
   If a build ever fails to find them, launch GoLand from a shell that has that
   dir on `PATH`, or add it to the run config's Environment.

## Bumping LLVM later (e.g. to 23)

1. `pacman -S mingw-w64-x86_64-llvm` to get the newer package; check
   `llvm-config --version`.
2. Re-copy go-llvm at a version that has the matching `llvm_config_llvmNN.go`,
   re-add the `windows` block (update `-lLLVM-NN`), and switch the tag to
   `llvmNN` (here and in `.idea/runConfigurations/llvm_lang.xml`).

## Gotchas

- **The `llvm22` tag must be on every go command** (build, run, test, vet) and
  in GoLand's custom tags — otherwise no `llvm_config` file is active, go-llvm's
  C++ can't find headers, and it won't compile.
- **`libLLVM-22.dll` is a runtime dependency** (shared link). It's in
  `C:\msys64\mingw64\bin`; keep that on `PATH` when running the exe elsewhere,
  or ship the DLL alongside it.
- **"undefined reference" to C++ symbols** = a toolchain mismatch (system/UCRT
  Go or gcc leaking in, or MSVC LLVM). Check `go env CC CXX` both point at
  `C:\msys64\mingw64\bin`.
